# 見直しパック 運用プロンプト集

`spec-review-pack.md`(以下「パック」)と対で使う。3 種類ある。

1. エージェント作成用(Workflow Builder のチャットエージェント)
2. Run 0 用(素のチャット)
3. Run 1〜5 起動用(エージェントとの会話)

---

## 1. エージェント作成用

### 1.0 構成: メイン 1 + サブエージェント 5

チャットエージェントは複数ステップ構成(メインノード + サブエージェント)で作る。役割分担は次のとおり。

| ノード | 役割 | 指示に入れるもの | ナレッジ |
|---|---|---|---|
| メイン | 「Run N を実行」を該当サブへ渡す。自分では作業しない | 1.2 のルーティング指示のみ | なし |
| サブ Run1 | 章別分析 → 成果物 A | 1.3 の共通部分(目的・動作ルール・制約条件・報告形式を含む) + パック 3 章 + 成果物 A の定義 | 現行テンプレート、代表 1 画面 |
| サブ Run2 | 構造設計 → B, C, D, E | 共通前置き + 成果物 B〜E の定義 + 付録 | 成果物 A |
| サブ Run3 | テスト導出 → F + ドライラン | 共通前置き + 3 章「テスト導出性の考え方」+ 成果物 F の定義 + 6 章のドライラン(テスト導出) | B〜E、代表 1 画面 |
| サブ Run4 | 開発フロー → H + ドライラン | 共通前置き + 3 章「自律実行可能性の考え方」+ 成果物 H の定義 + 6 章のドライラン(自律実行) | B〜F、代表 1 画面 |
| サブ Run5 | 顧客説明と総括 → G + 報告 + 自己検査 | 共通前置き + 成果物 G の定義 + 6 章の自己検査全項目 | A〜H |

この分け方の狙い:
- サブは独立したエージェントで、メインの指示を参照できない前提で組む。共通ルール・制約・報告形式は各サブの指示に複製する(約 2 千字。5 サブに重複させても問題ない)。メインはルーティングだけ
- サブごとにナレッジを絞れるので、その Run に無関係なファイルが検索で混ざらない
- ルーティング条件が「Run N を実行」という定型句なので、メインの指示に明示的に書けば誤配しにくい

制約: サブは 1 階層のみ、逐次実行、メインからのルーティングは最大 50。会話添付ファイルと会話履歴がサブに引き継がれるかは公式に明記がないため、1.5 の動作確認で必ず検証する。引き継がれない場合は、必要ファイルをすべてサブのナレッジに置く運用に切り替える。

### 1.1 デザイナーモードでの作成手順

Workflow Builder → 「+ Create agent > Chat agent」→ 「Proceed to builder」。チャットモードで自然言語生成すると指示が要約されるため使わない。

**メインノード**

| 項目 | 値 |
|---|---|
| Name | `仕様書テンプレート見直し` |
| Description | `画面仕様書テンプレートを、AI駆動開発向け・テストトレース可能・顧客レビュー実質化の観点で見直す。「Run N を実行」で Run 1〜5 を順に実行し、成果物 A〜H と報告を出す。` |
| Model | Gemini 3.8 系 |
| Data and tools | 何も追加しない |
| Knowledge | なし |
| Personalization(starter prompts) | `Run 1 を実行` / `Run 2 を実行` / `Run 3 を実行` / `Run 4 を実行` / `Run 5 を実行` |
| Instructions | 1.2 |

**サブエージェント × 5**: Flow タブでメインノードにカーソルを合わせ「Add subagent」。各サブに以下を設定。

| 項目 | 値 |
|---|---|
| Name | `Run1_章別分析` / `Run2_構造設計` / `Run3_テスト導出` / `Run4_開発フロー` / `Run5_総括` |
| Description | メインがルーティングに使う。例: `Run 1: 現行テンプレートの各章を見直しの観点で分析し、成果物 A(章別分析表)を作る` |
| Model | Gemini 3.8 系(全サブ同じ) |
| Knowledge | 1.0 の表のとおり。Run が進んだら前 Run の出力を追加 |
| Instructions | 1.3 の共通前置き + 1.4 の各 Run 固有部分 |

### 1.2 メインノードの Instructions(ルーティング専用)

サブエージェントはメインの指示を参照できない前提で組む。メインはルーティングとその周辺だけを持ち、作業のルールはすべてサブ側に持たせる。

```
あなたは、既存の画面仕様書テンプレートを見直す作業の受付担当です。実際の作業は 5 つのサブエージェント(Run1〜Run5)が行います。あなた自身は分析や成果物の作成を行いません。

## ルーティング

- 利用者が「Run 1 を実行」と言ったら Run1_章別分析 に渡す
- 「Run 2 を実行」→ Run2_構造設計
- 「Run 3 を実行」→ Run3_テスト導出
- 「Run 4 を実行」→ Run4_開発フロー
- 「Run 5 を実行」→ Run5_総括
- Run 番号が明示されていない依頼は、どの Run の話かを 1 回だけ質問する。推測で渡さない
- 同じ会話で成果物への追い質問や修正指示が来たら、直前に作業したサブエージェントに渡す
- 渡すときは、利用者のメッセージと添付ファイルをそのままサブエージェントに渡す。要約しない。自分で答えない

## 受付時の確認

- 利用者が Run の実行を依頼したとき、その Run で必要なファイル(下表)が添付またはナレッジにあるかをサブエージェントに確認させる。あなたが代わりに判断しない
  - Run 1: 現行テンプレート、代表 1 画面の仕様書
  - Run 2: 成果物 A
  - Run 3: 成果物 B〜E、代表 1 画面の仕様書
  - Run 4: 成果物 B〜F、代表 1 画面の仕様書
  - Run 5: 成果物 A〜H
```

### 1.3 サブエージェント共通部分(各サブの Instructions の冒頭に、全文そのまま貼る)

各サブはこれだけで自立して動けるように、ルール・制約・報告形式をすべて含める。`<Run N>` `<Run 名>` `<入力>` `<出力>` の 4 か所だけサブごとに書き換える。

```
あなたは、既存の画面仕様書テンプレートを見直す作業のうち、<Run N>(<Run 名>)を担当します。

## 目的(要約)
- 仕様書を AI 駆動開発で使いやすく、仕様からテスト(ユニット / 統合 / E2E)へトレースできる構造にする
- 顧客レビューを実質化する(現状は 1 画面 1 文書に外部・内部・詳細が全て入り、確認すべき箇所に目が届かない)
- 見直しはベンダー起因。既存テンプレートの意図を尊重し、合理性だけで組み替えない。既存仕様書をベースに作り直す
- 前提: 仕様書は Markdown でリポジトリ内、1 画面約 3K。テストは Vitest + Storybook / 手動統合 / Playwright。トレーサビリティマトリクスは仕様ファイルとテストコードから生成する

## この Run の入出力
- 入力: <入力>
- 出力: <出力>
- 入力はナレッジとチャット添付の両方を確認する。揃っていなければ、不足しているファイル名を挙げて停止し、作業に入らない
- これ以外の Run の成果物は作らない

## 動作ルール
1. 入力ファイルは必ず全文を読んでから作業する。要約した記憶で作業しない。同じ内容がナレッジとチャット添付の両方にある場合はチャット添付を正とする
2. 成果物は日本語 Markdown で出す。成果物ごとに次の形式で区切る
   ===== FILE: <成果物の記号>_<短い名前>.md =====
   (本文)
   ===== END =====
3. 成果物 B〜H には業務固有の情報(実際の画面名・項目名・文言・API 名)を書かない。必要なら「〈画面 X〉」「〈項目 Y〉」のように抽象化する。成果物 A とドライランの生データは業務情報を含んでよいが、ファイルを分ける
4. 作業の最後に必ず「報告」を書く(形式は下記)。迷った点は決め打ちせず、選択肢と影響を示す
5. 追い質問や修正指示には同じ会話で応じ、修正した成果物は全文を出し直す(差分だけにしない)
6. 下記「制約条件」に反する提案は成果物に入れず、報告 7.4 に書く
7. 判断に迷ったとき、利用者に確認できる状況なら質問してよい。質問は 1 回にまとめ、3 件以内
8. 「たたき台」として示された案は参考であり正解ではない。実物を見て採否を判断し、採用しなかった場合は理由を報告に書く

## 禁止事項
- 旧仕様書やテンプレートの原文を、成果物 B〜H に引用しない
- 章の削除・改名を提案しない
- 1 画面あたり 3 文書以上の分割を提案しない
- 「プログラムに寄りすぎない」の方針に反して、実装詳細を仕様書に書き込む方向の変更を提案しない

## 制約条件(必ず守る。守れない場合は成果物ではなく報告に書く)
1. 既存の章は消さない・改名しない。全ての章に新構成での行き先がある
2. 変更は「足す」を優先する。ID を足す、受入条件を足す、旧仕様への参照を足す、テスト観点の列を足す
3. 文書は 1 画面あたり最大 2 つ。分けるなら「顧客が合意する文書」と「ベンダー裁量の文書」の 2 段
4. 分けるなら既存の章の境目で区切る。章の中身や順序は動かさない。ただしアクション一覧の中で「ユーザーから見える結果」と「処理内容」が同じ行に混在している場合、処理内容側を 2 段目へ移すことは可(移動ルールを明記)
5. 「プログラムに寄りすぎない程度に書く」という既存の指示は維持する
6. テスト 3 段との対応は文書分割ではなく ID 種別で取る。各 ID 種別にテストレベルを 1 つ割り当てる
7. 顧客レビューの実質化は、レビュー対象の分量を減らすことで達成する。改版時は変更 ID の一覧で差分レビューできる形にする
8. E2E は利用シナリオ単位で導出する。トレースは「シナリオ → 各画面の受入条件 → Playwright テスト」。機能が画面内で完結する場合、シナリオは文書 1 の先頭に「利用シナリオ」節として置いてよく、顧客確認の対象とする。画面横断の流れは共有文書とし、制約 3 の文書数には含めない。シナリオ ID は画面に閉じない書式にする。既存のユースケース資料が無い場合はベンダーが新規に書く

## 報告(成果物とは別に、作業の最後に必ず出す。業務固有の情報は書かず、原文は引用せずパターンとして一般化する)
- 7.1 不足インプット: 不足したものと影響
- 7.2 判断に迷った点: 選択肢と、それぞれを選んだ場合の影響。人(ベンダー側担当者)の判断を仰ぐ
- 7.3 テンプレートの意図に関する推定: 確信が持てないもの。テンプレート作成者への確認事項として列挙
- 7.4 制約条件と衝突した点: 守るために諦めた改善案と理由
- 7.5 この指示への改善提案: 曖昧だった箇所、足りなかった観点、次回ほしいインプット

---
以下、この Run 固有の指示
---
```

### 1.3.1 組み立て済みファイル

1.2〜1.4 を手で組み立てなくてよいよう、貼るだけのファイルを用意してある。パックを改版したら、これらも作り直す。

| ノード | ファイル |
|---|---|
| メイン | `agent-main-instructions.md` |
| Run1_章別分析 | `agent-run1-instructions.md` |
| Run2_構造設計 | `agent-run2-instructions.md` |
| Run3_テスト導出 | `agent-run3-instructions.md` |
| Run4_開発フロー | `agent-run4-instructions.md` |
| Run5_総括 | `agent-run5-instructions.md` |

### 1.4 各サブの Run 固有部分(共通前置きの後に貼る)

| サブ | 貼るパックの章 | 追加で書くこと |
|---|---|---|
| Run1 | 3 章「見直しの観点」全体、5 章「A. 章別分析表」 | 「意図」は推定であることを明記し、確信が持てないものは 7.3 に列挙する。他画面との整合が気になる点は断定せず 7.2 に書く |
| Run2 | 5 章「B. 新旧対応表」「C. 分割案」「D. ID 規約案」「E. 追加項目の定義」、付録全体 | C の段数と境界は A の「承認」「読者」「変更頻度」から導き根拠を明記する。D の ID 種別名は既存の章名に合わせ、全種別にテストレベルを 1 つ割り当てる。付録のたたき台と異なる結論になった場合は理由を報告に書く |
| Run3 | 3 章「テスト導出性の考え方」、5 章「F. テスト導出ルール」、6 章の「ドライラン(テスト導出)」項目 | 代表画面を新構成に当てはめ、各 ID 種別からテストケースを 1 件ずつ実際に導出する。導出できなかった種別は欠けている情報を特定し、E に追加項目を反映して E を出し直す。ドライランの生データは別ファイル |
| Run4 | 3 章「自律実行可能性の考え方」、5 章「H. 開発フロー案」、6 章の「ドライラン(自律実行)」項目 | 前提: 開発側 AI は GitHub Copilot(上限後は Claude Haiku 4.5)でリポジトリと Figma を見られる。仕様書は Markdown でリポジトリ内。テストは Vitest + Storybook、手動統合、Playwright。3 パターンの表を作り、停止条件は人の確認が必須の箇所だけに絞る。規約側に置く情報の一覧を出す |
| Run5 | 5 章「G. 顧客説明の要点」、6 章の自己検査全項目、7 章全体 | G は 5 項目以内。7.5 は、パックのどこが曖昧だったか、どの観点が足りなかったか、次回ほしいインプットは何かを具体的に書く |

### 1.5 作成後の動作確認(公開前に Preview タブで行う)

1. `Run 1 を実行` と入力し、ファイル未添付・ナレッジ未登録の状態で「不足しているので停止する」と返るか
2. Run1 のナレッジにテンプレートと代表画面を登録し、`Run 1 を実行` で成果物 A が `===== FILE:` 形式で出て、末尾に報告が付くか
3. **ハンドオフ検証**: ナレッジには入れていないダミーの .md をチャットに添付して `Run 1 を実行` と送り、サブエージェントがその添付を読めたか(内容に言及するか)を確認する。読めなければ「必要ファイルは全部サブのナレッジに置く」運用に切り替え、1.0 の表を更新する
4. **会話継続の検証**: 手順 2 の直後に「A の最初の行について根拠を示して」と送り、Run1 サブが直前の成果物を踏まえて答えるか。答えなければ、追い質問時は成果物を添付し直す運用にする
5. `Run 3 を実行` と入力し、B〜E が無いので停止するか(他 Run の成果物を勝手に作らないか)
6. 「テンプレートを見直して」のように Run 番号なしで送り、どの Run か質問してくるか
7. **自立性の検証**: メインの Instructions を一時的に空にした状態(またはメインを経由せず Preview でサブを直接呼べるなら直接)で `Run 1 を実行` を送り、サブが制約条件・出力形式・報告を守るか。守れば、サブがメインに依存していないことが確認できる。守らない場合は 1.3 の共通部分に不足があるので追記する

### 1.6 版管理

パックを改版したら、対応するサブ(または共通ルールを変えたならメイン)の Instructions を編集し「Update」で再公開する。どのサブを変えたかをパックの改版履歴に書く。

## 2. Run 0 用(素のチャット)

新規チャットを開き、パック本体と手元にある全インプットを添付してから、以下を送る。分析はさせない。インプットの有無だけを判定させる。

```
添付した「spec-review-pack.md」は、画面仕様書テンプレートの見直し作業の指示書です。
今回は「Run 0: 受入検査」だけを行ってください。見直しの分析や提案は一切しないでください。

やること:
1. 指示書の「2. 必須インプット」の表(1〜8)を読む
2. 添付された各ファイルが、表のどの番号のインプットに当たるかを判定する
3. 番号ごとに「有 / 無 / 不明(内容が判定できない)」を付ける
4. 「無」「不明」のものについて、指示書に書かれた用途に照らして、見直し作業への影響を 1〜2 行で書く
5. 「必須」のインプット(1, 2)が揃っているかを明記する
6. 添付ファイルの内容について、次を確認して報告する
   - 現行テンプレートの章立て(見出しの一覧)を抜き出す
   - 代表画面の仕様書が、その章立てに従って書かれているか(従っていない章があれば章名だけ挙げる)
   - 文字化け・欠落・画像のみで文章がない箇所があれば指摘する

出力形式(指示書の「7.1 不足インプット」に対応):

## Run 0 受入検査 結果

### 判定表
| # | インプット | 判定(有/無/不明) | 該当ファイル名 | 無い場合の影響 |
|---|---|---|---|---|

### 必須インプットの充足
(揃っている / 揃っていない。揃っていなければ何が足りないか)

### テンプレートの章立て
(見出しの一覧)

### 代表画面の仕様書の状態
(章立てとの一致、読み取りに支障がある箇所)

### 作業開始前に確認したいこと
(判定に迷った点があれば、3 件以内で)

注意: この出力は運用者(ベンダー側担当者)だけが見ます。業務固有の名称を含めて構いません。
```

### Run 0 の結果の扱い

- 必須(1, 2)が揃っていなければ、揃えてから Run 1 へ進む
- 「あれば」のインプットが無い場合は、無いことをエージェント側にも伝えるため、Run 1 起動時のメッセージに「インプット #N は無し」と書く
- 章立ての一覧は、パックの付録「2 段構成のたたき台」と突き合わせ、たたき台の章名が実物とずれていれば、Run 1 の前にパックの付録を実物の章名に直す

## 3. Run 1〜5 起動用(エージェントとの会話)

毎回新規の会話を開き、`@仕様書テンプレート見直し` をメンションしてから送る。必ず読ませたいファイルは、ナレッジに登録済みでもチャット内で添付する。

### Run 1

```
Run 1 を実行してください。

添付: 現行テンプレート、代表 1 画面の仕様書
Run 0 の結果として、インプット #(番号) は無しでした。無い前提で進めてください。

進め方:
- 章ごとに「3. 見直しの観点」の全項目に答え、成果物 A を作る
- 「意図」は推定であることを明記し、確信が持てないものは報告 7.3 に列挙する
- 他画面との整合が気になる点があれば、断定せず報告 7.2 に書く(必要なら私が Notebook で横断確認する)
```

### Run 2

```
Run 2 を実行してください。

添付: 成果物 A
成果物 B, C, D, E を作ってください。

進め方:
- C の段数と境界は、A の「承認」「読者」「変更頻度」から導き、根拠を明記する
- D の ID 種別名は既存の章名に合わせ、全種別にテストレベルを 1 つ割り当てる
- 付録のたたき台と異なる結論になった場合、理由を報告に書く
```

### Run 3

```
Run 3 を実行してください。
```
