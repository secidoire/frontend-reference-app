# 仕様書テンプレート見直し 決定記録

このファイルは、見直しパック・プロンプト集・エージェント指示を設計した際の経緯と判断を記録したもの。改版時に「なぜこうなっているか」を参照するためのもので、Gemini や Copilot に渡す文書ではない。

作成: 2026-09-28。以後、判断を変えたらこのファイルに追記する(上書きしない)。

---

## 1. ファイル構成

| ファイル | 役割 | 渡す先 |
|---|---|---|
| `spec-review-pack.md` | 見直しの指示書本体(目的・観点・制約・成果物・報告) | エージェントの指示の素材。Run 0 では素のチャットに添付 |
| `spec-review-prompts.md` | エージェント作成手順、Run 0 プロンプト、Run 1〜5 起動メッセージ | 運用者 |

## 2. 前提と制約(所与のもの)

- 目的: AI 駆動開発向けで、仕様→テストのトレースができ、顧客レビューが実質化する仕様書テンプレートに、既存テンプレートを作り直す
- 立場: ベンダー起因の見直し。既存テンプレートの意図は尊重する(合理性の外にある事情を含む)
- 対象: フロントエンドの画面仕様書から着手。今回対象の機能は画面内で完結している
- 現状の仕様書: Markdown、リポジトリ内、1 画面約 3K。章立ては「画面概要説明 / 画面イメージ / 項目一覧 / 取得項目 / 送信項目 / チェック一覧 / メッセージ一覧 / アクション一覧 / アクション詳細」。アクション一覧・詳細には「プログラムに寄りすぎない程度に書く」という指示がある
- 問題: 1 画面 1 文書に外部・内部・詳細が全部入っており、顧客レビューが形骸化している(レビューしている体になっている)
- テスト: ユニット = Vitest + Storybook、統合 = 手動、E2E = Playwright
- ユースケース資料: 無い
- AI 環境:
  - 文書側: Gemini Enterprise。見えているのはエージェント・ワークフロー・Notebook・素のチャット。プロジェクト機能とスキル機能は無い。モデルは 3.8 系が選べる。1 画面分しか見せられない(リポジトリ全体は不可)
  - リポジトリ側: GitHub Copilot(リポジトリ・Figma を参照可)。AI クレジットは 15,000 あるが組織上限に先に当たる。上限後は Claude Haiku 4.5 に限定
  - 業務情報は Claude(この会話)には見せられない

## 3. 主要な判断と理由

### 3.1 Claude の役割は「判断基準・問い・出力形式の設計」に限定する
- 決定: 構造そのもの(段数、境界、ID 規約)は Claude が決めず、実物を見られる Gemini が提案し、人が判断する。Claude はパック(判断材料)を作る
- 理由: Claude は業務文書を見られない。Claude が構造を決めると、既存テンプレートの意図を踏み潰す
- 経緯: 当初 Claude 側で 4 層 → ディレクトリ分割 → 2 段 → 3 段と構造案を出し続けたが、「直前の発言に引きずられて振り回している」「見直し自体は Gemini にさせると言っている」と指摘され、役割を切り直した
- 却下: Claude が構造を確定してから Gemini に転記させる案

### 3.2 既存テンプレートの意図を尊重する(制約条件 1, 2, 4, 5 の根拠)
- 決定: 章は消さない・改名しない。変更は足す形を優先。分けるなら章の境目。「プログラムに寄りすぎない」は維持
- 理由: ベンダー起因の見直しであり、テンプレート作成者の意図や運用経緯は合理性の外にある。顧客にも「構造は変えていない、ID と受入条件を足した」と説明できる
- 却下: アクション詳細を AI にコードから逆生成させる案(「プログラムに寄りすぎない」の意図と衝突)

### 3.3 文書は 1 画面あたり最大 2 つ(制約条件 3)
- 決定: 「顧客が合意する文書 / ベンダー裁量の文書」の 2 段まで。3 段以上にしない
- 理由: 文書が分割されすぎると困る(利用者の判断)。テストが 3 段(ユニット/統合/E2E)でも、トレースは文書分割ではなく ID 種別で取れるので、文書数を増やす必要はない
- 却下: 3 段案(画面仕様 / 受入仕様 / 実装設計)。説明しやすさはあったが分割過多
- 却下: 読者・変更頻度・所属の 3 軸でディレクトリ分割する案。既存構成を変えすぎ

### 3.4 テスト 3 段との対応は ID 種別で取る(制約条件 6)
- 決定: ID 種別ごとにテストレベルを 1 つ割り当てる。マトリクスは仕様ファイルとテストコードからスクリプトで生成し、未カバー ID を出す。CI で警告
- たたき台: 項目(表示状態)→Storybook、チェック→Vitest、受入条件→Playwright、データ連携→手動統合、アクション詳細→Vitest(ロジック)
- テスト側の埋め込み: Vitest はテスト名タグ、Playwright は annotations、Storybook は story 名/parameters、手動統合はテストケースを Markdown でリポジトリに置き ID を持たせる
- 理由: 手動統合テストもマトリクスに載せるには、ケース定義自体を機械可読にする必要がある

### 3.5 E2E はユースケース(利用シナリオ)単位で導出する(制約条件 8)
- 決定: トレースは「シナリオ → 各画面の受入条件 → Playwright」。画面内完結なら文書 1 の先頭に「利用シナリオ」節、画面横断なら共有文書(2 文書上限に含めない)。シナリオ ID は画面に閉じない書式
- 理由: 画面単位の受入条件だけでは、画面をまたぐ流れを検証する E2E を導出できない。ユースケース資料は無いため、ベンダーが新規に書いて顧客に確認してもらう位置づけにする(レビュー実質化のストーリーとも整合する)
- 経緯: 当初「ユースケースが無い場合は画面横断の E2E 導出を対象外」としたが、今回の対象が画面内完結と分かり、文書 1 内の節で扱う形に緩和した

### 3.6 顧客レビューの実質化は分量を減らすことで達成する(制約条件 7)
- 決定: 承認対象の文書を短くし、改版時は変更 ID の一覧で差分レビューできる形にする
- 理由: 全文レビューが形骸化するのは量の問題。受入条件を 1 行ずつ並べると読んだふりがしにくく、後で揉めたとき「AC-xxx に書いてある」で決着がつく
- 顧客向けストーリー: 問題の所在は「弊社の文書構成が確認箇所を絞れていなかった」とベンダー側に置く。効果は「レビュー負荷の集中」と「検証の透明性(どこまで自動確認されているか)」の 2 点を顧客メリットとして語る

### 3.7 見直しの観点に「テスト導出性」「自律実行可能性」を入れる
- 決定: 章ごとに「1 行からテスト 1 件を解釈なしで書けるか」「AI が質問せずに実装できるか(不足は仕様書に足すか規約側に置くか)」を評価させる。ドライラン 2 件(テスト導出、自律実行)を自己検査に入れる
- 理由: 当初の観点は「人がレビューしやすいか」に寄っていて、AI が自律して走れるか・テストを作らせやすいかを見ていなかった(利用者の指摘)
- 注意: 不足情報を全部仕様書に足すと肥大化し「プログラムに寄りすぎない」に反する。プロジェクト規約(AGENTS.md 相当)に置くべきものを分けさせる。規約整備は別トラック

### 3.8 開発フローは新規・改修・逆生成の 3 パターンで書かせる
- 決定: 成果物 H は 3 パターン別。改修では「変更 ID 一覧」を出力に含め、顧客差分レビューとテスト更新範囲の特定に使う。Figma は項目一覧の起点。仕様と実装の乖離は AI が報告し判断は人
- 理由: 実務は改修が多く、改修の経路が設計されていないとトレーサビリティが初回しか機能しない(利用者の指摘)

### 3.9 実行は Run 0〜5 に分け、文脈は成果物ファイルに持たせる
- 決定: 1 回で全成果物を出させない。各 Run は前 Run の出力ファイルだけを入力にする。出力は必ずファイル保存。会話履歴に頼らない
- 理由: Gemini 側は 1 画面分しか見せられず、1 セッションで A〜H を出すのは分量的に無理。「文脈は AI ではなく成果物に持たせる」原則
- 経緯: 当初パックは 1 回実行前提で書かれており、利用者の指摘で分割した

### 3.10 Gemini Enterprise の機能の使い分け(調査に基づく)
調査結果の要点(2026-09-28 時点の公式ドキュメント):
- 素のチャット: 指示を固定できない。保持期間(作成日基準)を過ぎると自動削除。.md 添付は 2 MB 上限
- チャットエージェント: 指示・モデル・ナレッジを固定。同じスレッドで追い質問可。チャット内添付も可。サブエージェントは 1 階層・逐次・最大 50。ノーコード作成はプレビュー。作成クォータあり(Standard 1 件/人/日、Plus 10 件、プール、下書きも消費)。既知の問題で 3.1 Pro 推奨の記載あり
- ワークフロー: 手順実行型。人の介入は「情報要求」「承認」の 2 種のみで、ステップ内の往復は不可。JSON スキーマで構造化出力可。自然言語生成では承認ステップを追加できない(UI で手動)。負荷時タイムアウトが既知の問題
- Notebook: ソースに厳密に根拠づける。300 ソース/ノートブック。生成物より横断参照向き
- プロジェクト・スキル: 御社環境では見えていないため使わない

決定:
- Run 0 は素のチャット(一回きり、基準固定不要)
- Run 1〜5 はチャットエージェント(観点と制約を指示に固定し、Run 間・画面間で同じ基準を担保)
- Notebook は全画面の旧仕様を入れた横断参照専用
- ワークフローは横展開(手順が固まった後)。往復が要る工程には使わない
- 経緯: 当初「エージェントは安定してから」と先送りしていたが、「分析や評価の往復ならエージェントのほうがいいのでは」という指摘を受けて比較し直し、最初から使う判断に変えた。プロジェクト機能を前提にした版も一度出したが、環境に無いため撤回

### 3.11 エージェントはメイン 1 + サブ 5、サブは自立型
- 決定: メインはルーティング+工程案内のみ。Run ごとにサブを置き、各サブの指示に「目的の要約・動作ルール・禁止事項・制約条件・報告形式」を丸ごと複製する。ナレッジはサブごとに絞る
- 理由: サブは独自ロジックを持つ独立したエージェントで、メインの指示を参照できる保証がない。指示の長さ問題も解ける(パック全文を 1 か所に入れなくてよい)。ナレッジのスコープが切れる
- 未確認: チャット添付と会話履歴がサブに引き継がれるかは公式に明記がない。公開前の Preview で検証(プロンプト集 1.5)。渡らなければ必要ファイルを全部サブのナレッジに置く
- 却下: 単一ノードで始めてから分割する案(利用者の指摘で、サブを最初から使う方向に変更)
- 却下: パック全文をナレッジに置く案(ナレッジは検索参照扱いで、必ず読ませたい制約が落ちる恐れ)

### 3.12 Copilot クレジットの使い方
- 決定: 上限前に「考える仕事」を済ませる: マトリクス生成スクリプト、テスト命名規則と lint、パイロット 1 画面の ID 埋め込み。以後の横展開は Haiku でも回る機械的作業にする
- 決定: 指示の置き場所はリポジトリ内のプロンプトファイルに寄せる(Gemini / Copilot / Haiku のどれで実行しても同じ指示が使える)
- 理由: 上限に当たるタイミングが読めないため、弱いモデルに落ちる前提で設計する

## 4. 未決事項(Run の結果を見て決める)

1. 2 段にするか 1 文書のままか、境界はどこか(Run 2 の C)
2. 受入条件を顧客承認の対象に含めるか、確認のみか
3. Storybook の story の現状の単位(コンポーネント単位か画面状態単位か)。表示状態のトレース先にできるか
4. 納品形式が 1 文書である必要があるか(あるなら結合生成)
5. チャット添付・会話履歴がサブエージェントに引き継がれるか(Preview で検証)
6. 改修時に変更 ID を機械的に出すための構造(各行に版を持つか、1 行 1 ID で git 差分から拾うか)
7. プロジェクト規約(AGENTS.md 相当)の整備トラックをいつ始めるか(Run 4 の一覧が入力)

## 5. 議論の中で出て却下・撤回した案(再提案しないため)

| 案 | 却下理由 |
|---|---|
| Claude が構造を確定して Gemini に転記させる | Claude は実物を見られず、既存の意図を踏み潰す |
| 4 層(画面 / 業務ルール / 実装 / 受入条件)を独立文書に | 分割過多 |
| specs/ 配下を shared / api / screens/<id>/5 ファイルに分割 | 既存構成を変えすぎ |
| 3 段(画面仕様 / 受入仕様 / 実装設計) | 最大 2 文書の方針に反する |
| アクション詳細を AI にコードから逆生成 | 「プログラムに寄りすぎない」の意図と衝突 |
| Notebook で Run 1(章別分析)を作る | 生成向きでない。横断参照専用に |
| プロジェクト機能をパックの入れ物にする | 環境に無い |
| スキル機能に工程を落とす | 環境に無い。リポジトリ内プロンプトファイルで代替 |
| エージェントは安定してから作る | 往復の基準固定はエージェントのほうが向く |
| 単一ノードで作って後で分割 | サブを最初から使い、指示の長さとナレッジのスコープを解く |
| メインに共通ルールを持たせてサブに参照させる | サブはメインの指示を参照できる保証がない |
| ユースケースが無いなら画面横断 E2E は対象外 | 今回は画面内完結なので文書 1 内の節で扱える |
