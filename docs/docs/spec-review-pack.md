# 画面仕様書テンプレート見直しパック

このファイルは、既存の画面仕様書テンプレートを見直す作業を AI(Gemini)に依頼するための指示書です。
ここに書かれた目的・観点・制約に従って見直し案を作成し、指定の成果物と報告を出力してください。

---

## 0. 作業の進め方

この見直しは **複数回に分けて実行する**。各回(Run)は前の回の出力ファイルだけを入力として動き、1 回で全成果物を出そうとしない。運用者(人)が Run を順に起動し、出力を保存して次の Run に渡す。

1. まず「1. 目的と制約」「4. 制約条件」を読み、遵守事項を把握する
2. 起動された Run の指示(「0.1 実行ガイド」の該当行)に従い、その Run の成果物だけを作る
3. 判断に迷う点は決め打ちせず、その Run の末尾に「7. 報告」の形式で列挙する
4. Run 0 で不足インプットがあれば、作業に入らず報告して停止する

### 0.1 実行ガイド(運用者向け)

使えるのは Gemini Enterprise のアシスタント(チャット)、エージェント(Workflow Builder のチャットエージェント)、ワークフロー、Gemini Notebook Enterprise の 4 つ。プロジェクト機能とスキル機能は使えない前提で組む。

**基本方針: Run 1〜5 はチャットエージェント 1 体で回す。** 理由は、見直しの観点と制約条件をエージェントの指示に固定でき、Run 間・画面間で同じ基準が使われることを担保できるため。素のチャットは毎回添付が必要で、評価基準がセッションごとに揺れ、保持期間(作成日基準)を過ぎると履歴が消える。

#### エージェントの作り方

| 設定 | 内容 |
|---|---|
| 構成 | **メイン 1 + サブエージェント 5(Run ごと)**。メインは「Run N を実行」を該当サブへルーティングし、全 Run 共通の動作ルールと制約条件を持つ。各サブはその Run の成果物定義と観点だけを持つ。サブは 1 階層・逐次実行の制約あり |
| 指示(Instructions) | メイン: 動作ルール + パックの 1・4・7 章。サブ: 共通前置き + その Run に関係する章と成果物定義。**ナレッジではなく指示に入れる**(ナレッジは参照用に検索される扱いで、全文を必ず読ませたい制約条件や観点が落ちる恐れがある) |
| ナレッジ | サブごとに絞る。Run1: テンプレート + 代表 1 画面 / Run2: A / Run3: B〜E + 代表画面 / Run4: B〜F + 代表画面 / Run5: A〜H。Run が進むたびに追加する(1 ファイル 20 MB、100 ファイルまで、.md 可) |
| モデル | Gemini 3.8 系(メイン・サブとも) |
| データソース・ツール | 不要。オフにしておく |
| ハンドオフ検証 | チャット添付ファイルと会話履歴がサブに渡るかは公式に明記がない。公開前に Preview で検証し、渡らない場合は必要ファイルをすべてサブのナレッジに置く運用にする |
| 版管理 | 本パックを改版したら、該当するサブ(共通ルールならメイン)の指示を編集して「Update」で再公開する。パックの版 = エージェントの版 |

具体的な設定値・指示文・動作確認手順は `spec-review-prompts.md` の 1 章にある。

作成にはクォータがある(Standard: 1 件/人/日、Plus: 10 件/人/日、いずれも組織でプール。下書きも消費する)。設定内容を固めてから作る。

#### Run の割り当て

| Run | 内容 | ツール | 入力 | 出力 |
|---|---|---|---|---|
| 0 | 受入検査 | 素のチャット(一回きりで基準固定が不要) | 本パック + 全インプットを添付 | 報告 7.1(不足インプット)のみ。不足なしなら「揃っている」と一言 |
| 1 | 章別分析 | エージェント(必要なら Notebook で横断確認) | ナレッジ: テンプレート + 代表 1 画面(チャット内でも添付) | 成果物 A |
| 2 | 構造設計 | エージェント | ナレッジ: A(チャット内でも添付) | 成果物 B, C, D, E |
| 3 | テスト導出 | エージェント | ナレッジ: B〜E + 代表 1 画面 | 成果物 F + ドライラン(テスト導出)の結果 + E の修正 |
| 4 | 開発フロー | エージェント | ナレッジ: B〜F + 代表 1 画面 | 成果物 H + ドライラン(自律実行)の結果 + E / H の修正 |
| 5 | 顧客説明と総括 | エージェント | ナレッジ: A〜H | 成果物 G + 報告 7.2〜7.5 + 自己検査結果 |

Run の起動は、毎回新規の会話で `@エージェント名 Run N を実行` と書き、その Run で必ず読ませたいファイルはナレッジにあってもチャット内で添付する。Run の途中で追い質問や修正指示を重ねてよい(往復はエージェントの会話内で行う)。出力は必ずファイルとして保存し、次の Run のナレッジに追加する。会話履歴に頼らない。

#### 他の機能の使いどころ

- **素のチャット**: Run 0 と、エージェントが作れない場合の代替。代替時は本パックを毎回添付し、1 Run 1 セッションで回す
- **Notebook**: 全画面分の旧仕様書をソースとして 1 ノートブックに入れておき、「この用語は他画面でどう使われているか」「このチェックは他画面にもあるか」のような横断確認に使う。ソースに厳密に根拠づける道具なので、構造案や意図の推定のような生成には使わず、参照用に限る
- **ワークフロー**: Run 0〜5 の手順が固まり、複数画面で同じ手順を繰り返す段階(横展開)になってから組む。変換 → 承認(人間参加型ステップ)→ 次工程、の形で「停止条件」を承認ステップに置き換え、成果物の型は JSON スキーマで固定する。ステップ内で往復はできないので、往復が必要な工程には使わない。承認ステップは自然言語生成では追加できず、UI で手で足す

成果物 H の「指示の置き場所」は、Gemini 側では「チャットエージェントの指示文」または「リポジトリに置くプロンプトファイル」、リポジトリ側(Copilot)では「Copilot 用の指示ファイル」を指すものとして書く。Gemini Enterprise のスキル機能は使わない。

Run の出力は業務情報を含まない形(成果物 B〜H)と含む形(A、ドライランの生データ)を分けて保存し、含まない形だけをパック改善の検討に回す。

## 1. 目的と制約

### 目的
- AI 駆動開発で使いやすい仕様書にする(AI が実装・テストの入力として扱える構造)
- 仕様 → テスト(ユニット / 統合 / E2E)の成果物トレーサビリティを確保する
- 顧客レビューを実質化する。現状は 1 画面 1 文書に外部仕様・内部仕様・詳細が全て入っており、顧客が本当に確認すべき箇所に目が届かず、レビューが形骸化している

### 立場
- 見直しはベンダー起因。既存テンプレートで実現しようとしていた意図は尊重する。合理性だけで構造を組み替えない
- 既存仕様書をベースに作り直す。ゼロから設計しない

### 前提環境
- 仕様書は Markdown、リポジトリ内。1 画面あたり約 3K
- テスト: ユニット = Vitest + Storybook、統合 = 手動、E2E = Playwright
- トレーサビリティマトリクスは手書きせず、仕様ファイルとテストコードから生成する前提

作業前に以下が揃っているか確認する。不足があれば報告して停止する。

| # | インプット | 用途 | 必須 |
|---|---|---|---|
| 1 | 現行テンプレート本体 | 見直し対象 | 必須 |
| 2 | 代表 1 画面分の実仕様書(テンプレートに従って書かれたもの) | 各章の実際の使われ方の確認 | 必須 |
| 3 | 画面一覧(画面 ID と名称) | ID 規約の設計 | あれば |
| 4 | 既存テストの命名規則・ファイル配置の説明 | テスト対応の設計 | あれば |
| 5 | 顧客レビューの現状の運用(誰が・いつ・何を承認しているか) | 分割境界の判断 | あれば |
| 6 | 用語集 | 用語の統一 | あれば |
| 7 | ユースケース / 業務フロー / 業務シナリオの資料(要件定義書・基本設計書の該当章でも可) | E2E テストの導出元。画面横断の受入条件の設計 | あれば(無い場合は影響大、下記参照) |
| 8 | Figma の構成(フレーム・コンポーネントの命名規則、画面との対応)の説明 | 項目一覧の起点としての Figma の扱い(成果物 H) | あれば |

## 3. 見直しの観点

テンプレートの **各章について** 以下を答える。答えは章ごとの表にまとめる(成果物 A)。

| 観点 | 問い |
|---|---|
| 意図 | この章は何のために存在するか。テンプレート作成者が実現したかったことは何か(章名・記述の指示・実仕様書の書かれ方から推定し、推定であることを明記) |
| 読者 | 主に誰が読むか(顧客業務担当 / 顧客テスト担当 / ベンダー開発者 / ベンダー QA / AI) |
| 承認 | 顧客の合意・承認の対象か、ベンダー裁量か |
| 変更頻度 | 何をきっかけに変わるか(顧客合意 / 実装変更 / API 変更 など) |
| テスト対応 | どのテストレベル(Storybook / Vitest / 手動統合 / Playwright / なし)の検証対象になるか |
| AI 入力 | AI が実装する際の入力として、そのまま使えるか / 構造化が必要か / 不要か |
| テスト導出性 | この章の 1 行(1 項目)から、テストケース 1 件を **解釈なしで** 書けるか。書けない場合、何が欠けているか(前提状態 / 入力 / 操作 / 期待結果 / 判定基準 のどれか) |
| 自律実行可能性 | この章の情報は、AI が人に質問せずに実装を進めるために十分か。不足がある場合、それは **仕様書に足すべき情報** か、**プロジェクト規約側に置くべき情報**(コンポーネント設計規約、状態管理方針、API スキーマの参照先、共通 UI の使い方など)か。後者は仕様書に書かない |
| 現状の問題 | 実仕様書を見て、この章で起きている問題(書きすぎ / 書き足りない / 他章と重複 / 曖昧) |

この表から、章ごとに「残す / 足す / 区切る」のいずれかを導く。

### テスト導出性の考え方
仕様書の役割は「AI や人がテストを書くときに、仕様を読み直して解釈しなくて済む」ことにある。目安として:
- チェック一覧の 1 行 = ユニットテスト 1 件になるか(対象項目・条件・入力例・期待される結果・表示メッセージが行に揃っているか)
- 項目一覧の表示条件 1 つ = Storybook の story 1 つになるか(状態が列挙されているか、「〜の場合」が曖昧でないか)
- 受入条件の 1 行 = E2E テスト 1 件になるか(前提状態・操作・期待結果が Given / When / Then で分かれているか)
- 取得項目・送信項目の 1 行 = 手動統合テストの確認項目 1 つになるか(API・項目・変換ルールが対応づいているか)

「作りやすさ」には人が書く場合と AI に書かせる場合の両方を含む。AI に書かせる場合は、仕様の行をそのままプロンプトに貼って成立する粒度が目標。

### 自律実行可能性の考え方
目標は「文書 1 + 文書 2 + プロジェクト規約」を渡された AI が、人に質問せずに実装・テストを完了し、人は成果物のレビューだけを行う状態。
- AI が質問しそうな点を列挙し、それぞれの答えの置き場所を決める(仕様書 / プロジェクト規約 / 都度の指示)
- 仕様書に足すのは「その画面固有で、顧客合意またはベンダー設計判断に当たる情報」のみ。実装の作法に関する情報は規約側に寄せ、仕様書を肥大化させない(制約 5 との整合)
- 開発の各段階をスキルまたはプロンプトとして固定できるよう、段階ごとの入力ファイル・出力・停止条件を明確にする(成果物 H)

## 4. 制約条件

以下は必ず守る。守れない場合は成果物ではなく報告に書く。

1. **既存の章は消さない・改名しない。** 全ての章に新構成での行き先がある
2. **変更は「足す」を優先する。** ID を足す、受入条件を足す、旧仕様への参照を足す、テスト観点の列を足す
3. **文書は 1 画面あたり最大 2 つ。** 分けるなら「顧客が合意する文書」と「ベンダー裁量の文書」の 2 段。3 つ以上に分けない
4. **分けるなら既存の章の境目で区切る。** 章の中身や順序は動かさない。ただしアクション一覧の中で「ユーザーから見える結果」と「処理内容」が同じ行に混在している場合、処理内容側を 2 段目へ移すことは可(その場合は移動ルールを明記)
5. **「プログラムに寄りすぎない程度に書く」という既存の指示は維持する。** 実装詳細を仕様書に書き込む方向の変更はしない
6. **テスト 3 段との対応は文書分割ではなく ID 種別で取る。** 各 ID 種別にテストレベルを 1 つ割り当て、マトリクスは ID で生成できる形にする
7. **顧客レビューの実質化は、レビュー対象の分量を減らすことで達成する。** 承認対象の文書は短くし、改版時は変更 ID の一覧で差分レビューできる形にする
8. **E2E はユースケース(利用シナリオ)単位で導出する。** トレースは「シナリオ → 各画面の受入条件 → Playwright テスト」とし、E2E テストはシナリオ ID を持ち、そのステップが受入条件 ID を参照する。
   - 機能が画面内で完結する場合: シナリオは文書 1 の先頭に「利用シナリオ」節として置いてよい(「この画面で達成したいこと」の一覧、数行程度)。顧客確認の対象とする
   - 画面横断の流れがある場合: シナリオは画面ごとの文書には含めず、共有文書として扱う(制約 3 の「1 画面あたり最大 2 つ」には含めない)
   - どちらの場合も、シナリオ ID は画面に閉じない書式にし、後で共有文書へ移してもテスト側のタグを書き換えずに済むようにする
   - 既存のユースケース資料が無い場合、シナリオはベンダーが新規に書き、顧客に確認してもらう位置づけとする

## 5. 成果物

全て日本語 Markdown。業務固有の情報(実際の画面名・項目名・文言など)は成果物 B〜H には含めない。含める必要がある場合は「〈画面 X〉」「〈項目 Y〉」のように抽象化する。

### A. 章別分析表
「3. 見直しの観点」の表。章ごとに 1 行。

### B. 新旧対応表
| 旧章 | 新構成での位置(文書 1 / 文書 2、章名) | 変更種別(残す / 足す / 区切る) | 変更内容 | 根拠(A のどの観点から) |

### C. 分割案
- 段数(1 または 2)と、2 段なら境界となる章
- 各文書の読者・承認者・改版トリガー
- 境界の根拠。「4. 制約条件」との整合を確認した旨
- 2 段にしない場合はその理由

### D. ID 規約案
- ID 種別の一覧(例: 画面 / 項目 / チェック / メッセージ / アクション / 受入条件 / データ連携)。種別名は既存の章名に合わせる
- 各種別の書式、採番単位、一意性の範囲
- **各種別が紐づくテストレベル**(Storybook / Vitest / 手動統合 / Playwright / なし)
- 各項目に持たせる旧仕様への後方参照の書式(旧仕様の章番号・行など)

### E. 追加項目の定義
足す項目(受入条件、テスト観点列、後方参照など)それぞれについて、置き場所・書式・記入例(抽象化)・記入者。

### F. テスト導出ルール
ID 種別ごとに、仕様の 1 行からテストケースをどう組み立てるかのテンプレート。AI にテストを書かせるときの指示文としてそのまま使える形にする。

| ID 種別 | テストレベル | 仕様行の必須列 | テスト名の組み立て | 前提 / 操作 / 期待結果の対応 |
|---|---|---|---|---|

必須列が現行テンプレートに無い場合は、E の追加項目として定義する。

### G. 顧客説明の要点
ベンダー起因の見直しとして顧客に説明する際の要点を 5 項目以内で。問題の所在はベンダー側の文書構成に置く。効果はレビュー負荷の集中と検証の透明性の 2 点を顧客メリットとして書く。

### H. 開発フロー案
新テンプレートを前提に、1 画面の開発がどう流れるかを **開発パターン別に** 段階ごとの表にする。各段階がそのままスキル / プロンプトの入出力契約になる粒度で書く。

| 段階 | 実行者(AI / 人) | 入力ファイル | 出力 | 停止条件(人の確認が必須の箇所) | 指示の置き場所(案: Gemini チャットエージェントの指示 / リポジトリ内プロンプトファイル / Copilot 用指示ファイル) |
|---|---|---|---|---|---|

少なくとも以下の 3 パターンについて表を作る。

1. **新規作成**: Figma → 利用シナリオ → 文書 1 → 顧客レビュー → 文書 2 → 実装 → テスト作成 → トレーサビリティ検査 → 統合テスト(手動)
2. **改修**: Figma(差分)+ 既存実装 + 既存の文書 1 / 2 → 文書 1 / 2 の更新 → **変更 ID 一覧** の出力 → 変更 ID のみ顧客レビュー → 実装 → 影響テストの更新(マトリクスから変更 ID に紐づくテストを特定)→ トレーサビリティ検査
3. **逆生成(移行)**: 既存実装 + 旧テンプレートの文書 → 新テンプレートの文書 1 / 2 を起こす → 実装との乖離の報告 → ID 埋め込み。今回の移行作業そのもの

各パターンで共通して決めること:
- **Figma の位置づけ**: 項目一覧は Figma の要素から機械的に起こし、旧仕様の記述をそれに紐づける順序を基本とする。Figma と仕様の対応(フレーム名・コンポーネント名と項目 ID の関係)をどう持つか
- **既存実装の位置づけ**(改修・逆生成): 仕様と実装が食い違ったとき、どちらを正とするかの判断を誰がするか。AI は乖離を報告するまでとし、判断は人
- **変更 ID 一覧の書式**(改修): 顧客への差分レビュー依頼とテスト更新範囲の特定の両方に使える形

あわせて、**プロジェクト規約に置くべき情報の一覧**(仕様書には書かないが AI の自律実行に必要なもの)を出す。内容の作成は本作業の対象外、項目名と用途まで。

## 6. 出力の自己検査

成果物を出す前に以下を確認し、結果を報告に含める。

- [ ] 旧テンプレートの全章が B に登場し、行き先がある
- [ ] 改名した章がない
